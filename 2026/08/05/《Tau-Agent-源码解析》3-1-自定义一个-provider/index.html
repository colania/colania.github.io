一、自定义一个 provider

因为 TAU 里边是没有 DeepSeek 的，所以我们需要自己去实现一个。大体实现我就不讲了，可以让 AI 来帮你实现。下面这份示例代码（examples/deepseek_tau_tools.py）是核心，看懂它就懂了「怎么把一个 OpenAI 兼容的模型接进 Tau」。

几个关键点：

  • 复用 OpenAICompatibleProvider：DeepSeek 是 OpenAI 兼容接口，所以不用从零写 Provider，只要配 base_url 和 api="openai-completions"。
  • mcp_tools_as_tau_tools 是适配层：把 MCP 风格工具定义包成 Tau 的 AgentTool，execute_fn 内部再桥接回本地 registry。闭包里用 tool_name=spec.name 默认参数避免循环变量陷阱。
  • debug_sse=True 会打印三层调试信息：原始 SSE 行 → 去掉 data: 的 JSON → Tau parser 生成的 ProviderEvent，这正是下面分析流程用的素材。

5. 一次运行的事件生命周期（总结）

把上面串起来，一次自定义 provider + DeepSeek 的运行，事件流是这样一条线：

顺序 事件 含义
1 agent_start Agent 启动
2 turn_start 第一轮开始
3 message_start/end (user) 用户提示入上下文
4 message_start/end (assistant 空占位) 标记本轮 provider/model
5 message_update (text_delta ×N) 模型文本流式返回
6 tool_execution_start / tool_execution_end ×2 模型调工具，Tau 执行并返回
7 message_start/end (toolResult ×2) 工具结果写回 messages
8 turn_end 第一轮结束（stopReason=toolUse）
9 turn_start → message_update → turn_end 第二轮：模型汇总（stopReason=stop）
10 agent_end 携带完整消息列表，循环结束

这套事件序列，和你在第一篇看到的「Events are the Contract」、第二篇 run_agent_loop 的两层 while、第三篇 provider 把 SSE 解析成 AssistantMessage/ToolCall 完全吻合——自定义 provider 接入后，上游所有机制一字未改，只是 openai-completions 后面跑的模型从 GPT 换成了 DeepSeek。
