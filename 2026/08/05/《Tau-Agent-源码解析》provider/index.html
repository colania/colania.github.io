8月 5, 2026

本来今天想的是写tools.py这个文件，但是心血来潮，突然想先了解一下provider.py这个文件，隐隐感觉知道大模型怎么返回 tools 以后，再去看 tools 会更加清晰一点。而且通过今天的了解，对于 Codex、Claude Code 这种编码工具调用大模型，有了更深的一些理解。那么，现在就开始吧。

一、provider 文件全貌：它到底在做什么

provider 这一层（对应第一篇说的 tau_ai）做的事，和「封装成 AgentTool」正好相反——它不生产工具，而是把 tau_coding 层注册进来的 AgentTool 和 AgentMessage 翻译成各家 API 的请求格式，再把模型流式返回的原始 chunk 解析封装回 Tau 统一的 AssistantMessage / ToolCall。一句话：它是 Tau 和不同大模型之间的翻译官。

二、Protocol 与鸭子类型：为什么不用继承也能即插即用

这里有个让我觉得巧妙的点：各家 provider（比如 openai_compatible.py 里的 OpenAICompatibleProvider）并没有显式继承 ModelProvider，却能被当成 ModelProvider 使用。

原因在于 ModelProvider 是一个 Protocol——Python 类型系统里的「接口约定」。它只描述「一个对象应该有哪些方法」，不要求对象显式继承它。这背后就是 Python 的鸭子类型（运行时思想：走起来像鸭子、叫起来像鸭子，就当鸭子用），而 Protocol 给鸭子类型补上了静态类型检查能力。三者的区别：

概念 主要作用
鸭子类型 运行时思想，直接调用对象的方法
Protocol 给鸭子类型增加静态类型检查能力
抽象基类 ABC 要求显式继承或注册

Protocol 本身不实现方法、也不在运行时强制检查，主要帮助：IDE 补全、mypy/pyright 检查、明确模块间接口契约、减少不必要的继承关系。因此在 Tau 中，只要某个类实现了兼容的 stream_response()，不管它是 OpenAICompatibleProvider、AnthropicProvider 还是测试用的 FakeProvider，都能直接传给 agent loop：

这就是 Tau 能做到「换模型不碰核心层」的根本原因——和第一篇讲的「核心层与 CLI/TUI 解耦」是同一套哲学，只不过这里解耦的是「模型供应商」。

六、串回 loop：provider 产出的消息去哪了

到这里，正好接上第二篇 _assistant_events 那段。provider 吐出的是 AssistantMessageEvent 这一族 Provider 事件，canonicalize_provider_stream() 先转成 agent 层统一的 ToolCallStart/EndEvent、AssistantDoneEvent 等，然后被 loop 里的 _assistant_events 进一步翻译成 MessageStartEvent / MessageUpdateEvent / MessageEndEvent 抛给前端。

而那一条 AssistantMessage（里面装着 ToolCall）会被 loop 写进 messages，紧接着执行工具，工具结果变回 ToolResultMessage 再追加进 messages——下一轮 stream_response 调用时，这些消息又作为上下文喂回模型 API。这就是开头那张图里「ToolResultMessage → 下一轮 API 请求」闭环的来历，也是第二篇说的「messages.append(...) 持续累积」的真实源头。

总结

provider 这一层看着是「调个 API」，但有几个设计点值得记住：

  1. 它是翻译官不是生产者：把 AgentTool/AgentMessage 翻成各家 API 请求，再把原始 chunk 解析回 Tau 统一的 AssistantMessage/ToolCall，绝不自己造工具。
  2. 核心接口只有 stream_response：靠 Protocol + 鸭子类型实现即插即用，换模型不碰核心层，和「核心层解耦」哲学一脉相承。
  3. 流式靠拼接：文本和工具参数都是分片到达，parser 用 content_parts / _ToolCallBuilder 累加，最后 json.loads 拼出完整 ToolCall。
  4. 结束信号各家不同：Chat Completions 看 finish_reason+[DONE]，Responses API 看自己的事件类型，但都被归一化成 Tau 统一的轮次结束事件。
  5. 闭环在 messages：provider 产出的 AssistantMessage 经 loop 执行工具后，工具结果作为下一轮上下文回到 stream_response，形成持续对话的环。

下一篇就可以放心去看 tools.py 了——现在我们知道 AgentTool 是怎么被翻译进 API 请求、又怎么在模型返回里被认出来的，再看工具侧会非常顺。
