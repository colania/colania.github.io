从Tau harness 理解harness 工程

什么是 harness。harness 的概念是这样子：Harness 工程（Harness Engineering，又译驾驭工程）是 AI 智能体（AI Agent）时代的系统工程范式。它指为大模型或 Agent 提供并构建运行环境、安全沙箱、约束机制、工具权限与反馈回路的底层基础设施。
Harness 就是马鞍，顾名思义，它就是为了限制马的自由发挥，让马来按照人的想法来行动。但是，套上马鞍以后，你是让马赛跑还是让马耕地，这就是工具的事情了。
AI 的 Harness 可以理解为一个小型的 Agent Runtime 工程，它不是模型 Provider，也不是工具实现，而是负责把这些组件组织起来。

运行入口：prompt / continue_ / _run

Harness 对外暴露两种「启动一轮」的方式：

  • prompt / prompt_message：带一条新用户消息启动。
  • continue_：不带新消息，纯粹让 Agent「接着把刚才没干完的活继续干」。比如你 cancel 了，想让它从断点继续，就调 continue_。

两者都先调 _ensure_not_running() 防止重入——Harness 是单线运行的（他是个 code agent，只用单线程来跑），跑着的时候不能再跑：

这里抛的报错信息本身就是最好的文档：想中途插话请用 steer / follow_up，别直接再开一轮。这跟前面讲的两条队列设计严丝合缝。

真正的循环在 _run 里，它本质就是一个 async generator：

  1. 新建一个 signal 令牌并挂到 self._current_signal，这样 cancel() 才能在这个生命周期内生效。
  2. 把配置、历史消息、队列、钩子一股脑交给 run_agent_loop（就是你在 agent-loop.md 里详解的那个主循环）。注意 get_steering_messages / get_follow_up_messages 传的是两个 drain 方法——循环每需要新指令时就来 drain 队列，queue_mode 在这里生效。
  3. await self._notify(event) 在前，yield event 在后：每产生一个 AgentEvent，先广播给所有订阅者（TUI 渲染、日志），再 yield 给外部调用方。所谓「事件即契约」，在这里就是一行 notify + 一行 yield。
  4. finally 里的清理最关键：
    • 如果这一轮是被取消的（signal.is_cancelled()），调 _append_interrupted_tool_results() 把「没来得及返回结果的工具调用」补成一条错误结果——否则会话历史里会出现「调了工具但没结果」的残缺记录，下次续跑就乱套了（详见下一节）。
    • 清掉 _current_signal、_running = False，让 Harness 回到可再次启动的状态。

两条消息队列：steering 与 follow_up

这是 Harness 最有意思的设计之一。它区分了两种「插话」意图：

  • steer（掌舵）：优先级高，会在下一轮工具执行之前被插进去。比喻一下——Agent 正要动手拧水管，你喊「先别动，换个扳手」，这就是 steer。
  • follow_up（跟进）：优先级低，等当前这一轮会话的完整链路走完之后才会被消费。比如 Agent 正在跑一连串工具，你说「跑完这批顺手把日志也清了」，它就等这波结束再处理。

队列怎么被消费，由 queue_mode 决定：

  • "one_at_a_time"：每轮只取队首一条，剩下的留着下一轮再说——适合「逐条引导」，避免一次性塞太多指令冲垮上下文。
  • "all"：一把全取空——适合「我不管中间过程，把这些要求全带上」的场景。

QueuedMessages 这个只读快照把 steering 和 follow_up 分开放，还提供 count 属性，方便前端展示「当前还有几条待处理消息」：

另外还有 clear_queues()、pop_latest_steering()、pop_latest_follow_up() 这些管理接口——后者用 pop()（从队尾取），意味着「最新插的话优先撤回」，符合直觉。

取消信号：SimpleCancellationToken

这是一个极简的「协作式取消」令牌。它不是线程中断、也不是异常强杀，而只是一个布尔标志。循环里的每一步（模型调用、工具执行）会去检查这个标志，发现被置位就主动停下来——这就是「协作式」的含义：礼貌地请求 Agent 收工，而不是暴力打断。

AgentHarness.cancel() 只是把当前这一轮的信号置位：

这对应 Harness Engineering 里的「人类监督」——骑手随时能拉缰绳，但马是按自己的步调优雅停下，不会原地翻车。

事件订阅：subscribe / _notify

核心层「事件即契约」的落地，靠的就是订阅机制：

几个关键点：

  • EventListener 可以是普通函数，也可以是 async 函数。_notify 用 isawaitable 判断，如果是协程就 await，否则直接调用。这样 TUI 的渲染器（可能要 await 更新界面）和普通日志回调都能挂上来。
  • subscribe 返回一个 unsubscribe 闭包：订阅者拿到的不是什么神秘的句柄，就是一个能把自己摘掉的函数。with suppress(ValueError) 保证重复取消也不报错。
  • list(self._listeners) 复制一遍再遍历：防止监听器在回调里又 unsubscribe 导致迭代时列表长度变化报错。这是写异步事件系统时很常见的防御手段。
  • **Harness 自己不消费事件**——它只负责把 AgentEvent` 转发出去。渲染、打印、落盘全是订阅者的事。这正是第一篇说的「Events are the Contract」。

中断恢复：_append_interrupted_tool_results

这是「让 Agent 跑得稳、不会翻车」的具体体现。当用户 cancel() 时，很可能 Agent 刚发出一个工具调用、但工具还没返回。如果不处理，历史消息里就会留下一个「悬空」的 AssistantMessage.tool_calls 没有对应的 ToolResultMessage。模型下次看到这段历史会困惑。

Harness 的做法是自动补一条错误结果：

逻辑拆解：

  • 先扫一遍已有的 ToolResultMessage，收集「已经正常返回过结果的 tool_call_id」到 returned_ids。
  • 再遍历所有 AssistantMessage 里的 tool_calls，凡是 id 不在 returned_ids 里的，说明「调了但没回音」——就补一条 ToolResultMessage，内容是 "Tool call interrupted by user"，并标 is_error=True。
  • 用 tuple(self._messages) 复制一遍再遍历，避免遍历时 append 修改原列表导致无限循环。
  • 用 returned_ids 集合做去重，保证同一条 call 只补一次。

这一手很「Harness Engineering」：用确定性的规则（补错误结果）代替对模型的软建议，保证会话历史永远是「工具调用必有结果」的自洽状态，下次 continue_() 续跑时模型不会踩坑。
