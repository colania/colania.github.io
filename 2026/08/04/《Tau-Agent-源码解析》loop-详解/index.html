Tau agent 解决方案
《Tau Agent 源码解析》loop.py 详解
Aug 4, 2026

在第一篇里，我们建立了 Tau 的整体心智模型：一次请求从 CodingSession.prompt() 一路走到 run_agent_loop()，再靠 AgentEvent 事件流把结果甩回前端。但 run_agent_loop() 内部到底是怎么一轮一轮跑的，我们留了个坑。

这一篇就专门把 tau_agent/loop.py 拆开讲。这个文件不大，注释里写得很直白——“Pure Pi-compatible provider/tool agent loop”（一个纯正的、和 Pi 兼容的 provider/tool 主循环）。它不依赖任何 CLI 或 TUI，是核心层 tau_agent 里最纯粹的一段逻辑。

一、文件全貌：它到底在做什么

一句话：loop.py 实现了一个**「模型说话 → 工具执行 → 再把结果喂回模型」的无限循环**，并且在每一小步都向外抛 AgentEvent，让前端去渲染。

整个文件导出的核心就是一个异步生成器函数：

注意它的返回类型是 AsyncIterator[AgentEvent]——这正好呼应第一篇讲的「Events are the Contract」。调用方不需要知道里面发生了什么，只要 async for event in run_agent_loop(...) 不断消费事件就行。

先看一下它吃进来的关键参数：

参数 类型 作用
provider ModelProvider tau_ai 层的模型供应商（OpenAI/Anthropic/…）
model str 具体模型名
system str 系统提示词
messages list[AgentMessage] 历史对话（会被持续追加）
tools list[AgentTool] 可用工具定义
prompts Sequence[AgentMessage] 本次新注入的提示（初始用户请求）
max_turns int | None 最多跑几轮，防止死循环
signal CancellationToken | None 取消令牌，用于中断
get_steering_messages Callable 每轮开始前注入的「转向」消息（相当于外部指挥）
get_follow_up_messages Callable 工具都跑完后注入的「后续」消息
before_tool_call / after_tool_call Callable 工具调用前后的钩子（可拦截/改写）

钩子这点很有意思：before_tool_call 可以返回一个 (blocked, reason)，直接把这次工具调用拦下来——这就是 Tau 做权限/安全拦截的扩展点。

二、入口与骨架：两层 while 套娃

run_agent_loop 的主体是两层嵌套循环，这是理解整个文件的关键：

  • 外层 while：处理「follow-up 消息」。当工具全部跑完、模型也不再要调工具时，如果外部通过 get_follow_up_messages 又塞了新指令，就 continue 再开一轮；否则 break 结束整个 Agent。
  • 内层 while：处理「一轮 turn 内可能连续多次调工具」。只要还有工具要跑（has_more_tools）或者有外部注入的 pending 消息，就继续。

四、内层主循环：一轮 turn 的三段式

内层循环是重头戏，每一轮 turn 大致分三段：注入转向消息 → 调模型 → 执行工具。

4.1 注入 steering 消息

get_steering_messages 在每一轮开始前都会被调用一次。它返回的「转向消息」会被追加进历史并发出去。这给了外部一个「在 Agent 每轮思考前悄悄塞指令」的能力——比如注入最新的代码上下文、或者人工干预方向。pending 用完即清空，避免重复注入。

4.2 调模型：_assistant_events

模型调用被包在 _assistant_events 这个辅助生成器里：

这里有一个异步生成器的小技巧，注释里专门解释了：Python 的 async generator 没法把一个「会 yield 的回调」干净地穿过普通 await，所以这里的做法是——一边 yield event 把模型流式事件转发出去，一边在循环结束时把最终的 AssistantMessage 抓住存到 assistant 变量里。这样外层既拿到了流式事件，又拿到了最终要写进历史的消息。

_assistant_events 内部做的事很简单：把 provider.stream_response() 吐出来的 AssistantStartEvent / AssistantMessageEvent / AssistantDoneEvent / AssistantErrorEvent 翻译成 Tau 自己的 MessageStartEvent / MessageUpdateEvent / MessageEndEvent。这就是 tau_ai 层和 tau_agent 层之间的「翻译层」——核心层只认自己的事件，不关心供应商原生事件长什么样。

4.3 执行工具：_execute_tool_call

模型回复里可能带若干个 tool_calls，逐个跑：

has_more_tools 在循环开头被设置，它直接决定了内层 while 要不要继续——只要这轮模型要调工具，内层就不会退出，会接着跑下一轮工具处理。

每个工具调用的事件序列是：ToolExecutionStartEvent →（可能有若干个）ToolExecutionUpdateEvent → ToolExecutionEndEvent → MessageStartEvent / MessageEndEvent（工具结果消息）。工具结果消息会被追加进 messages，这样下一轮模型就能看到工具的输出。

一轮 turn 跑完，发 TurnEndEvent 并 turn += 1。

五、工具执行的内幕：_execute_tool_call 与 _run_tool

看 _execute_tool_call，它的职责是把「一次工具调用」完整执行并转成事件：

这段逻辑非常「防御性」，把所有可能失败的点都列出来了：

  1. before_tool_call 拦截：外部钩子说不行，就直接返回错误结果，工具根本不执行。这是权限/安全闸门。
  2. 取消令牌：如果 signal.is_cancelled()，返回「Operation aborted」。
  3. 工具不存在：tools.get(call.name) 找不到就报「Tool xxx not found」。
  4. 正常执行：交给 _run_tool。

注意 before_tool_call / after_tool_call 这两个扩展点：一个在工具跑前决定要不要拦，一个在跑后还能改写结果（result, is_error = await after_tool_call(call, result, is_error)）。Tau 的权限系统、日志审计基本都是挂在这俩钩子上。

再看 _run_tool：

几个值得说的点：

  • 工具是隔离边界：注释里写了 # noqa: BLE001 - tools are an isolation boundary。任何工具抛出的异常都被捕获，转成 _error_result，绝不会让一个烂工具把整个 Agent 搞崩。这正是「工具即隔离边界」的工程实践。
  • CancelledError 单独 raise：取消信号必须向上传播，不能被吞掉，否则无法真正中断。
  • on_update 回调 + accepting 标志：工具执行过程中可以多次回调 on_update 推送部分进度（流式更新），但这些 update 只在 accepting=True（即没结束）时才被收集。工具返回后 finally 里把 accepting 置 False，防止工具在返回后还异步回调导致竞态。这个细节很体现写代码的人功力。

最后 _execute_tool_call 把 AgentToolResult 包成 ToolResultMessage 发出去，完成一轮工具调用。

六、容易被忽略的两个细节

6.1 _provider_context：别把空失败回合喂给模型

看注释就懂：Provider 不一定能接受「一个没有任何内容的 assistant 回合」。Tau 会把终态失败（error/aborted）且没内容的消息从历史里过滤掉，不污染下一次请求。而有内容的失败消息仍然保留——因为它可能是诊断需要的信息。这是一个很务实的取舍。

6.2 为什么用 new_messages 而不是全程 messages

前面提过，messages 是贯穿整个会话的累积历史（包括进 loop 之前就有的），而 new_messages 只记录本次 loop 运行产出的消息。最后 AgentEndEvent(messages=new_messages) 返回的就是「这次 Agent 干了啥」，调用方（比如 CodingSession）可以精准地把新增部分持久化到 JSONL，而不是每次都重写全量历史。

你会发现 loop.py 几乎没有「业务逻辑」——它不关心读文件怎么读、写代码怎么写，只负责把 provider、tool、session 三者用一套事件协议编排起来。这正好印证了第一篇的结论：核心层是「干净的大脑」，所有脏活（文件系统、CLI、UI）都在别处。

总结

loop.py 虽然叫「loop」，但它真正牛的地方不在循环本身，而在几处克制的设计：

  1. 纯事件流输出：AsyncIterator[AgentEvent]，前端只管消费，零耦合。
  2. 两层 while：外层管 follow-up 续命，内层管单轮工具链，分工清晰。
  3. 工具即隔离边界：异常全吞，取消信号必传，绝不让一个烂工具拖垮 Agent。
  4. 钩子即扩展点：before/after_tool_call 承载权限与审计，steering/follow_up 承载外部指挥。
  5. 防御性收尾：空失败回合过滤、错误兜底消息、双层 max_turns 检查——保证循环任何情况下都能终止。
